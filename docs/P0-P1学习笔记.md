## 1. 我们到底在做什么？

OpsMind 最终希望处理这样的任务：

> “设备 EQ-10023 今天一直报警，上周刚修过，帮我看看。”

最终系统会查询业务数据、检索维修资料，让模型综合分析，再在人工确认后执行工单写入。

**当前只完成到 P1，不具备 AI 诊断能力。** 你在实验中填写的诊断内容是手动输入的演示数据。

### P0 做了什么？

准备开发环境、依赖管理、配置读取、日志、测试基础，以及架构和数据库设计。

### P1 做了什么？

建立设备、员工、维修记录、工单四张表，提供查询、创建、更新接口，并验证它们确实能读写 MySQL。

你已经完成了：

~~~text
查询设备 → 查看维修记录 → 创建工单
    → 分配维修人员 → 填写诊断 → 关闭工单
~~~

### 当前项目的边界

- 有后端，没有专门制作的产品前端。
- /docs 是自动生成的接口调试页面，不是最终产品界面。
- 有固定的演示员工和基础业务权限检查，没有完整登录认证。
- 有手动工单操作，没有 Agent 审批流程。
- 当前仅适合本机学习和演示。

## 3. 虚拟环境与依赖文件

### 3.1 为什么需要 .venv？

不同项目可能需要同一个包的不同版本。独立虚拟环境可以减少项目之间的依赖冲突。

~~~text
OpsMind/
  .venv/  ← 这个项目使用的 Python 环境和依赖
~~~

PyCharm 应选择已有解释器：

~~~text
D:\project\OpsMind\.venv\Scripts\python.exe
~~~

下面的命令表示使用项目环境中的 Python：

~~~powershell
.\.venv\Scripts\python.exe -m pytest -q
~~~

其中 -m pytest 表示运行 pytest 模块，-q 表示减少输出。

### 3.2 三个文件分别做什么？

| 文件 | 作用 |
| --- | --- |
| pyproject.toml | 描述项目、直接依赖和工具配置 |
| uv.lock | 固定解析出的精确依赖版本 |
| .python-version | 记录项目选择的 Python 版本系列 |

执行：

~~~powershell
uv sync --locked --cache-dir .uv-cache
~~~

表示按锁文件同步项目环境；--locked 要求锁文件与项目依赖声明一致；--cache-dir 指定缓存位置。

**.venv 是实际安装的环境，uv.lock 是版本记录。它们不能互相替代。**

## 4. 配置与日志：P0 的核心代码

文件：[config.py](../src/opsmind/core/config.py)、[logging.py](../src/opsmind/core/logging.py)。

### 4.1 什么是配置？

配置是运行程序需要的设置，例如日志级别、数据库连接地址。把它们集中管理，可以避免散落在代码中。

~~~python
from opsmind.core.config import Settings

settings = Settings()
print(settings.log_level)
~~~

逐句理解：

1. import：从配置模块导入 Settings。
2. Settings()：创建配置对象，读取并校验配置。
3. settings.log_level：访问对象的日志级别属性。
4. print：把它输出到终端。

创建 Settings 本身不会自动查询数据库。

### 4.2 配置优先级

本项目通常按以下顺序取值：

~~~text
显式构造参数 > 环境变量 > .env 文件 > 代码默认值
~~~

例如：

~~~python
Settings(log_level="ERROR")
~~~

这里显式传入的 ERROR 优先。

在我们做过的实验中：

| 条件 | 最终值 |
| --- | --- |
| 只有代码默认值 INFO | INFO |
| .env 写 WARNING，没有环境变量覆盖 | WARNING |
| .env 写 WARNING，环境变量写 ERROR | ERROR |

在同一个 PowerShell 终端中：

~~~powershell
$env:OPSMIND_LOG_LEVEL = "ERROR"
.\.venv\Scripts\python.exe -c "from opsmind.core.config import Settings; print(Settings().log_level)"
Remove-Item Env:OPSMIND_LOG_LEVEL
~~~

最后一条只删除当前终端中的环境变量，不会修改 .env。

通过这个终端启动的程序会继承环境变量；它不会自动影响 PyCharm 中另一个单独运行的进程。修改 .env 后，已经运行的后端也需要重启才能重新加载配置。

### 4.3 为什么 VERBOSE 会报错？

配置代码限定了允许值：

~~~python
log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"] = "INFO"
~~~

Literal 表示只能使用列出的值。传入 VERBOSE 后，Pydantic 报 ValidationError，不会悄悄退回 INFO。

这是在程序启动时尽早发现错误。

读 Python 报错时，先看最后几行的异常类型、字段名和实际输入，再根据需要向上看调用过程。

### 4.4 SecretStr 能做什么？

只使用假密码演示：

~~~python
from pydantic import SecretStr

password = SecretStr("demo-password")
print(password)  # 显示 **********
print(password.get_secret_value())  # 显示 demo-password
~~~

SecretStr 减少意外打印秘密的风险，但：

- 不是加密。
- 不会阻止程序主动取出原文。
- 不会自动清洗所有日志。

数据库连接需要使用原始凭据，但不能把原文打印或写入日志。.env 保存本地配置，.env.example 只提供可提交的空值或示例。

### 4.5 日志是什么？

日志是程序运行时留下的事件记录：

~~~text
2026-09-12T07:01:46Z INFO opsmind configuration ready
~~~

依次表示时间、级别、模块、事件说明。

常见日志级别从低到高：DEBUG、INFO、WARNING、ERROR、CRITICAL。配置 INFO 时，DEBUG 消息不会输出，INFO 及以上会输出。

日志帮助排查问题；它不等于数据库里的业务记录，也不应该记录密码或完整敏感请求。

## 5. Git：保存项目版本

### 5.1 最常用的流程

~~~text
编辑文件 → git add → 暂存区 → git commit → 本地版本记录
~~~

~~~powershell
git status
git add .
git status
git commit -m "描述这次完成的变化"
git log --oneline -5
~~~

- git status：查看当前变化。
- git add：选择这次准备提交的内容。
- git commit：保存一个本地版本。
- git log：查看提交记录。
- 本地提交不会自动上传到 GitHub。

每次提交前检查文件列表，不要把本地秘密放进去。.gitignore 能忽略尚未跟踪的文件；如果秘密已经被跟踪或提交，单纯补充忽略规则不能把它从历史中移除。

### 5.2 我们遇到过的两种提示

**dubious ownership：** 初始化仓库的沙箱账号和你运行 Git 的账号不同，Git 要求明确是否信任该目录。你已经为这个项目添加了 safe.directory。

**LF will be replaced by CRLF：** 换行符转换提示。LF 和 CRLF 是两种行结束表示，不代表 git add 失败。

中文文件名显示转义字符时，可以设置：

~~~powershell
git config core.quotepath false
~~~

这些 Git 提示与 Codex 的“沙箱进程启动失败”不是同一个问题；safe.directory 不会修复沙箱。

## 6. HTTP 接口：浏览器怎样和后端交流？

### 6.1 一次请求包含什么？

以查询设备为例：

~~~text
GET http://127.0.0.1:8000/api/v1/equipment/EQ-10023
~~~

| 部分 | 意思 |
| --- | --- |
| GET | 请求方法：查询 |
| 127.0.0.1 | 自己这台电脑 |
| 8000 | 服务监听的端口 |
| /api/v1/equipment/EQ-10023 | 请求路径，指定查询设备 |

常见方法：

| 方法 | 本项目用途 | 成功状态码 |
| --- | --- | --- |
| GET | 查询设备和历史 | 200 |
| POST | 创建工单 | 201 |
| PATCH | 部分更新工单 | 200 |

三个参数位置也要区分：

- **路径参数**：/equipment/EQ-10023 中的编号。
- **查询参数**：?limit=20&offset=0 中的分页设置。
- **请求体**：创建或更新工单时填写的 JSON。

### 6.2 JSON 是什么？

JSON 是一种传输数据的文本格式：

~~~json
{
  "id": 1,
  "name": "演示供电设备",
  "assigned_to": null
}
~~~

- {}：对象，包含字段名和值。
- []：数组，可以包含零个或多个元素。
- 字符串使用双引号。
- null：此处没有值。
- JSON 的 null 转到 Python 中通常对应 None。
- JSON 不是 Python 字典本身，虽然写法很像。

### 6.3 响应怎么看？

- Response body：主要返回内容，例如设备信息或错误说明。
- Response headers：附加信息，例如 content-type。
- content-type: application/json：正文采用 JSON 格式。

| 状态码 | 在当前项目中的例子 |
| --- | --- |
| 200 | 查询或更新成功 |
| 201 | 工单创建成功 |
| 403 | 操作员工无权限或不可用 |
| 404 | 设备或工单不存在 |
| 409 | 状态冲突，例如修改已关闭工单 |
| 422 | 参数或输入不符合要求 |
| 503 | 数据库未配置或操作不可用 |

状态码说明大类；错误体中的 code 进一步指出原因：

~~~json
{
  "error": {
    "code": "equipment_not_found",
    "message": "Equipment does not exist."
  }
}
~~~

code 便于程序识别，message 便于人阅读。

/docs 中的 Undocumented 表示这个响应没有在 OpenAPI 中完整声明，不表示业务代码没有处理它。当前错误响应的接口文档仍可完善。

## 7. 数据库：表、记录和关联

数据库中，一张表保存一类数据，一行是一条记录，一列是一个字段。

| 表 | 保存什么 |
| --- | --- |
| equipment | 设备 |
| employee | 员工 |
| maintenance_record | 维修记录 |
| ticket | 工单 |

### 7.1 ID 与业务编号不同

- id：内部记录标识，例如 1。
- equipment_no：业务设备编号，例如 EQ-10023。
- ticket_no：业务工单编号。

不要把设备编号 EQ-99999 理解为整数 99999；完整编号是字符串 "EQ-99999"。

### 7.2 主键、外键与唯一约束

- **主键**：唯一标识本表一条记录，例如设备 id。
- **外键**：关联另一张表的记录，例如维修记录 equipment_id。
- **唯一约束**：防止业务编号等字段重复。

你看到的维修记录：

~~~text
id = 1             这条维修记录自己的 ID
equipment_id = 1   它关联设备 ID 1
maintained_by = 2   它关联员工 ID 2
~~~

维修记录 id 和设备 id 都是 1 只是数值恰好相同，不是同一个含义。

员工用 ID 关联，是因为姓名可能重复，也可能变化。员工 ID 也不等于登录凭据。

### 7.3 为什么设备退役后保留记录？

设备还被工单和维修记录引用，而且历史需要追溯。我们通过状态停用设备，不直接清空历史。

外键的 RESTRICT 删除规则会阻止删除仍被引用的设备。首版也没有提供删除接口。

## 8. 从接口代码理解 Python 基础

文件：[api/routes.py](../src/opsmind/api/routes.py)。

~~~python
@router.get("/equipment/{equipment_no}", response_model=EquipmentRead, tags=["equipment"])
def read_equipment(equipment_no: EquipmentNo, session: DatabaseSession):
    return equipment.get_equipment(session, equipment_no)
~~~

### 8.1 def、参数和 return

- def：定义函数。
- read_equipment：函数名字。
- 括号中的内容：函数参数。
- return：返回执行结果。

最后一行可以拆成以下简化示意：

~~~python
result = equipment.get_equipment(session, equipment_no)
return result
~~~

### 8.2 @router.get 是什么？

@ 是装饰器语法。这里用于把下面的函数登记为 GET 接口的处理函数。

router 的前缀是 /api/v1，因此完整路径是：

~~~text
/api/v1/equipment/{equipment_no}
~~~

请求 /api/v1/equipment/EQ-99999 时，equipment_no 得到完整字符串 "EQ-99999"。程序不会自动删除 EQ-。

tags 用于接口文档分组，不负责业务权限。

### 8.3 冒号和箭头是什么？

~~~python
def get_equipment(session: Session, equipment_no: str) -> Equipment:
~~~

- equipment_no: str：期望参数是字符串。
- -> Equipment：期望返回设备对象。
- 这些叫类型标注。

普通 Python 类型标注本身不会自动检查所有运行时输入。FastAPI 和 Pydantic 会利用模型与标注做请求校验；这是框架提供的能力。

### 8.4 session 从哪里来？

调用 HTTP 接口时，用户不需要提交 session。项目用 FastAPI 的 Depends 机制提供它，称为**依赖注入**。

可以先理解为：框架按配置准备数据库会话，再传给接口函数。这个会话用于查询、跟踪对象变化和管理事务，不能简单等同于数据库本身。

相关代码：[api/dependencies.py](../src/opsmind/api/dependencies.py)。

## 9. 业务服务如何查询设备？

文件：[services/equipment.py](../src/opsmind/services/equipment.py)。

~~~python
def get_equipment(session: Session, equipment_no: str) -> Equipment:
    equipment = session.scalar(select(Equipment).where(Equipment.equipment_no == equipment_no))
    if equipment is None:
        raise BusinessError("equipment_not_found", "Equipment does not exist.", 404)
    return equipment
~~~

### 9.1 查询条件

~~~python
select(Equipment).where(Equipment.equipment_no == equipment_no)
~~~

意思是：查询设备表，筛选编号等于输入编号的记录。

- Equipment.equipment_no：数据库映射的编号字段。
- 右侧 equipment_no：函数收到的编号。
- ==：这里由 SQLAlchemy 组织为数据库比较条件。

概念上对应下面的 SQL（简化示意，实际由 ORM 生成并绑定参数）：

~~~sql
SELECT *
FROM equipment
WHERE equipment_no = :equipment_no;
~~~

不要把用户输入直接拼接成 SQL 字符串。

### 9.2 何时真正查询？

select(...).where(...) 组织查询；session.scalar(...) 执行查询并取第一个结果。

在这个查询中：
- 找到：得到 Equipment 对象。
- 没找到：得到 None。
- 设备编号具有唯一约束，所以最多匹配一台设备。

scalar 并不总是返回“设备对象”；它取决于你 select 的内容。

### 9.3 raise 是什么？

raise 抛出异常，中止当前正常执行路径。

这里抛出 BusinessError 后，API 错误处理器将其转换为 404 JSON。错误处理代码位于 [api/errors.py](../src/opsmind/api/errors.py)。

接口层接收 HTTP 参数，服务层判断设备是否存在。将来 Agent 查询设备时，也能复用服务，而不用复制业务逻辑。

## 10. ORM：为什么 Equipment 能代表一张表？

文件：[db/models.py](../src/opsmind/db/models.py)。

~~~python
class Equipment(Updated, Base):
    __tablename__ = "equipment"
~~~

- class：定义类。
- 类可以先理解为一种对象的结构与行为定义。
- Updated、Base 是父类，提供共享字段或 ORM 基础能力。
- __tablename__ 指明对应的数据库表。

字段示例：

~~~python
name: Mapped[str] = mapped_column(String(128))
~~~

表示 name 映射到数据库字段，在 Python 中是字符串，数据库字段最多 128 个字符。

| Python | 数据库 |
| --- | --- |
| Equipment 类 | equipment 表 |
| 映射属性 name | name 字段 |
| 查询得到的 Equipment 对象 | 一条设备记录 |

~~~python
equipment.name
equipment.location
~~~

这叫访问对象属性。

**大写 Equipment 是类，小写 equipment 是变量名。** 在服务函数里，这个变量保存查询得到的对象；在路由文件里，equipment 这个名字则是导入的服务模块。同一个名字在不同文件中可以代表不同东西，要看它在哪里定义或导入。

ORM 是“对象关系映射”。底层仍然由 MySQL 执行 SQL。

## 11. 从设备对象到 JSON：响应模型

文件：[schemas/business.py](../src/opsmind/schemas/business.py)。

路由写着：

~~~python
response_model = EquipmentRead
~~~

EquipmentRead 定义了对外返回结构，例如：

~~~python
class EquipmentRead(ReadModel):
    id: int
    equipment_no: str
    name: str
    # 这里只展示部分字段
~~~

父类 ReadModel 配置 from_attributes=True，使模型能够从 ORM 对象的属性中读取数据。

~~~text
数据库记录
  → SQLAlchemy 得到 Equipment 对象
  → EquipmentRead 读取、校验、整理字段
  → FastAPI 生成 JSON 响应
  → 浏览器显示
~~~

### 最重要的区别

| 名称 | 控制什么 |
| --- | --- |
| Equipment | 数据怎样映射到数据库 |
| EquipmentRead | 接口对外返回哪些数据 |

如果希望接口不返回 manufacturer，但数据库仍保留这个字段，优先修改 EquipmentRead。这里是理解题，不要求现在实际删字段。

响应模型可以减少无意暴露数据库字段的风险，但仍需要开发者正确选择字段，它不是完整的权限系统。

### 时间字段

- maintenance_at：实际维修时间。
- created_at：记录创建时间。
- updated_at：记录最近更新时间。

2026-09-01T08:00:00Z 中，T 分隔日期与时间，Z 表示 UTC，对应北京时间当天 16:00。

数据库按项目约定保存 UTC，API 会标明 UTC 时区。

## 12. 历史查询与分页

设备查询返回一个对象；维修历史可能有多条，所以返回列表：

~~~json
{
  "items": [
    {
      "id": 1,
      "equipment_id": 1,
      "maintained_by": 2
    }
  ],
  "limit": 20,
  "offset": 0
}
~~~

- items：当前页的数据。
- limit：最多返回几条，不是总数。
- offset：跳过前面几条。

当前仅一条记录，offset=1 时：

~~~json
{
  "items": [],
  "limit": 20,
  "offset": 1
}
~~~

状态码仍是 200，因为设备存在、查询成功，只是当前页没有数据。

**200 + [] 与 404 不同：前者是空的查询结果，后者是设备不存在。**

历史按时间倒序，再按 ID 倒序排序，让相同时间下的顺序也有确定规则。本项目采用简单的 offset 分页；并发新增数据时，跨页结果仍可能移动，不能把它理解为固定快照。

## 13. 创建工单：输入、存储、输出

创建请求：

~~~json
{
  "equipment_no": "EQ-10023",
  "title": "开机后持续报警",
  "description": "今天开机后一直报警，请安排检查。",
  "category": "electrical",
  "priority": "high"
}
~~~

路由参数中：

~~~python
data: TicketCreate
~~~

FastAPI 按 TicketCreate 校验请求体，通过后把模型对象传给函数。

~~~python
data.equipment_no
data.title
data.priority
~~~

### 三种模型不要混淆

| 模型 | 职责 |
| --- | --- |
| TicketCreate | 校验创建请求 |
| Ticket | 映射数据库记录 |
| TicketRead | 定义返回结果 |
| TicketUpdate | 校验局部更新请求 |

~~~text
JSON 请求
  → TicketCreate 校验
  → 服务检查设备和操作权限
  → Ticket 对象
  → 保存 MySQL
  → TicketRead
  → JSON 响应，状态码 201
~~~

请求中的 priority 如果是“随便”，不符合枚举，会返回 422。

extra="forbid" 表示拒绝未定义的额外字段。因此客户端不能偷偷提交 created_by，后端会拒绝。

### 输入校验不等于业务校验

- priority 是否是允许值：请求模型检查。
- 设备是否存在：需要查询数据库，由服务检查。
- 员工能否分配工单：由服务检查。

结构正确的请求仍可能不符合业务规则。

### 保存的关键步骤

在 [services/tickets.py](../src/opsmind/services/tickets.py) 中：

~~~python
session.add(ticket)
session.flush()
~~~

- add：把新对象加入 Session，准备保存。
- flush：把待处理变更发送到数据库，可以获得生成的 ID。
- flush 不等于最终提交。

服务用 with session.begin() 管理事务：正常退出时提交，出现异常时回滚。

每次成功 POST 都会创建一张新工单；当前接口没有自动去重或幂等键，因此不要反复点击创建按钮。

## 14. PATCH、状态与事务

### 14.1 PATCH 是局部更新

~~~json
{
  "assigned_to": 2,
  "status": "in_progress"
}
~~~

只修改提供的字段，其他字段保留。

员工 ID 2 来自你本机示例数据；换环境后不能保证仍为 2，应查询实际 ID。

代码通过：

~~~python
data.model_dump(exclude_unset=True)
~~~

只提取用户明确提交的字段。

“未提供”和“提供 null”不同：

- 不提供 assigned_to：保留现有值。
- 提供 assigned_to: null：请求清空处理人。
- 即使输入模型允许 null，业务规则仍可能拒绝清空，例如处理中必须有处理人。

### 14.2 本项目的状态规则

~~~text
open → in_progress → resolved → closed
待处理     处理中        已解决      已关闭
~~~

完整规则：

| 当前状态 | 允许转到 |
| --- | --- |
| open | in_progress、cancelled |
| in_progress | resolved、cancelled |
| resolved | in_progress、closed |
| closed | 终态，不再修改 |
| cancelled | 终态，不再修改 |

- 处理中及之后必须有处理人。
- resolved / closed 必须有诊断。
- resolved 可以重新进入处理。
- closed / cancelled 之后不能修改标题等字段。

你验证过：
- 没有诊断就解决：409 diagnosis_required。
- 补上诊断后解决：200。
- 关闭后修改标题：409 ticket_finalized。

这些是**本项目定义的业务规则**，不是所有工单系统必须完全相同。

### 14.3 事务是什么？

事务把一组数据库操作当成一个整体：

> 一起成功，或者失败时撤销这组未提交的修改。

例如一个请求同时修改标题和状态，如果状态不合法，标题也不应该被保存一半。

~~~python
with session.begin():
    # 检查规则
    # 修改记录
    session.flush()
# 正常退出：提交
# 出现异常：回滚
~~~

这个保证针对事务中的数据库操作，不会自动撤销邮件、文件写入等外部副作用。

更新工单还使用 with_for_update() 锁定对应行，让同时修改同一工单的事务有顺序。初学阶段先理解用途，不必立即深入锁机制。

### 15.3 测试有什么意义？

手工点击验证一次；测试代码把输入和预期结果记录下来，修改代码后可以重复检查。

~~~powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pytest --mysql -q
.\.venv\Scripts\ruff.exe check .
.\.venv\Scripts\ruff.exe format --check .
~~~

- 第一条：普通测试，真实数据库测试明确跳过。
- 第二条：运行包括真实 MySQL 的完整测试。
- Ruff 检查不等于业务功能测试。

P0 时有 4 项测试；P1 完成时有 44 项，包括 23 项真实 MySQL 测试。这是当前版本的结果，不是所有未来版本都必须保持这个数量。

passed 表示测试通过，failed 表示失败，skipped 表示没有执行，warning 表示需要关注的提示。跳过不能当作通过。

本项目测试库与开发库分开，测试通过事务回滚数据变化。自增 ID 即使回滚也可能出现空号，所以不能用 ID 最大值推断记录数量。

测试证明特定场景满足预期，不代表不存在任何缺陷。

### 15.4 当前已知提示

锁定的测试依赖产生两条上游弃用提示，当前不影响测试通过，也没有隐藏它们。

Git 换行提示、依赖弃用提示、业务 404 和真正的程序崩溃不是一类问题，要先看提示内容再判断。

## 16. Agent 审批：先记住原则

当前没有 Agent。后续模型可以提出“创建工单”的建议，但必须由程序检查是否得到有效确认。

只在提示词写“先询问用户”不能可靠地阻止工具直接写入。

~~~text
模型提出动作 → 程序保存待确认内容 → 用户确认
    → 程序核验具体动作和参数 → 执行写入
~~~

用户批准为设备 A 创建工单，不等于批准修改设备 B 的工单。批准要绑定具体动作。

事务与审批也不同：
- 审批：能不能执行这次动作。
- 事务：数据库修改如何一起成功或回滚。

## 20. 如何记录学习成果

每学完一个功能，尝试写三句话：

1. **我完成了什么？** 例如设备查询接口。
2. **它怎样工作？** 接收编号、调用服务、查询数据库、整理响应。
3. **我怎样确认它正确？** 有效编号返回 200，不存在编号返回 404，并有自动化测试。

求职时优先讲自己能解释、能复现的功能。当前可以讨论后端、数据库约束、事务和测试，不应宣称已实现 AI 故障诊断。

遇到不懂的地方，把章节或代码位置发来即可；不需要先把整份笔记背下来。
